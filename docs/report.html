Pocket: A Mobile Income Management System

Progressive Web Application

Group members: see GROUP_WORKLOAD.md

Lecturer: _______________________

Abstract

Many people receive income as a single balance and then spend until the money is gone. Pocket is a mobile web application that forces a different habit: income is placed first, then split into jars (Commitment, Food, Saving, Fun, or user-defined), and spending is allowed only from a chosen jar. If a jar is empty or the amount is higher than the remaining balance, the spend is blocked. The system runs in the phone browser, can be installed to the home screen, and stores data only on the device.

1. Introduction

1.1 Problem

How can a person on a phone separate incoming money into commitments, food, saving, and other uses, and be stopped from spending more than a given jar holds?

1.2 Objectives

  1. Record income in a ready-to-place pool.
  2. Split that pool with typed amounts, an even split, or a stored percentage plan.
  3. Allow spending only from a selected jar; reject overspend.
  4. Support transfers, monthly summary, history, and JSON backup.
  5. Ship as an installable PWA that works offline after the first visit.

1.3 Scope

In scope: single-user phone use, local storage, income/split/spend/transfer/report/backup.

Out of scope: bank login, multi-user cloud sync, native store listings.

Pocket implements the envelope method as a small PWA (Ramsey, 2013; CFPB, n.d.).

3. Methodology

Short iterative cycle: problem capture → prototype → overspend guards and % plan → transfers/report/backup → documentation and black-box tests. Static hosting only; no server.

4. Requirements

Non-functional: phone layout, offline cache, on-device data, two-decimal money.

5. Design

Phone browser → Pocket PWA → views + state → localStorage ("pocket.v1")

State fields: currency, unallocated, jars[] (id, name, color, balance, planPct), activity[] (id, at, type, title, detail, amount).

Rules: income raises the pool; a split cannot exceed the pool; a spend or transfer cannot exceed the source jar.

6. Implementation

HTML/CSS/vanilla JavaScript. Default plan 40% Commitment, 30% Food, 20% Saving, 10% Fun. Example: RM 5,000 → 2000 / 1500 / 1000 / 500. A Food spend of 2000 is blocked; 200 succeeds (Food 1300).

7. Testing

See TEST_PLAN.md (TC01–TC20). Development checks covered income, plan split, overspend block, valid spend, transfer, plan validation, export/import, and the app shell.

8. Conclusion

Pocket separates income on a phone and blocks overspending a jar. Future work: monthly caps, optional login backup, native wrapper.
